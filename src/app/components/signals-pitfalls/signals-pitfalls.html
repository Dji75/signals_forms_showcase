⚠️ Pièges des Signaux & Perte de Réactivité

Cette page présente les limites de la réactivité automatique d'Angular, l'asynchronisme, la détection de changements par référence et l'usage de untracked().

PIÈGE N°1

Perte de suivi des dépendances asynchrones

Les signaux enregistrent automatiquement leurs dépendances uniquement lors de l'exécution synchrone de la fonction réactive (effet, computed, template). Tout signal lu après un point d'asynchronisme (setTimeout, Promise, await, subscribe) ne sera pas enregistré.

valSync (Suivi synchrone) {{ valSync() }}
valAsync (Suivi asynchrone) {{ valAsync() }}

💡 Constat :
  • Si vous incrémentez Sync, l'effet se déclenche instantanément car valSync est synchrone.
  • L'effet affiche aussi la valeur actuelle de valAsync (car le setTimeout s'exécute).
  • Si vous incrémentez Async, l'effet ne se déclenche PAS ! Angular n'a pas détecté que valAsync a changé, car sa lecture était asynchrone et donc hors du radar de suivi.
PIÈGE N°2

Mutation directe d'objets (Comparaison par Référence)

Par défaut, un signal utilise l'égalité stricte (===) pour décider s'il doit propager un changement. Si vous modifiez un attribut d'un objet en place sans changer la référence de l'objet, Angular considère que l'état n'a pas changé.

Signal userObj() (État interne brut) : 
{{ userObj() | json }}
Signal dérivé userDescription() :
{{ userDescription() }}
💡 Constat :
  • Le bouton rouge incrémente l'âge de l'objet mais conserve la même référence mémoire. Bien que le JSON se mette à jour (car le template réévalue tout le composant), le signal calculé userDescription() ne se met PAS à jour car pour lui, l'objet n'a pas changé !
  • Le bouton vert retourne une nouvelle copie de l'objet (via { ...u }), provoquant instantanément le recalcul du signal dérivé.
PRATIQUE RECOMMANDÉE

Lectures non-suivies avec untracked()

Parfois, vous souhaitez lire la valeur d'un signal à l'intérieur d'un effet ou d'un calcul réactif sans que cette lecture ne crée une dépendance (c'est-à-dire sans réexécuter l'effet quand ce signal change). Vous pouvez entourer la lecture avec untracked().

countMain (Suivi normal) {{ countMain() }}
countUntracked (Ignoré) {{ countUntracked() }}

Logs d'exécution de l'effet :

@for (log of untrackedLogs(); track $index) {
{{ log }}
} @empty {
Aucun log. Cliquez sur un bouton pour modifier l'état.
}
💡 Constat :
  • Incrémenter countMain déclenche l'effet et affiche la valeur courante de countUntracked.
  • Incrémenter countUntracked ne déclenche PAS l'effet, car sa lecture est isolée dans un bloc untracked().
DÉFENSE DE CONCEPTION

Écritures interdites dans les effets (Anti-pattern)

Tenter de modifier un signal d'écriture (Writable Signal) à l'intérieur d'un effet ou d'un calcul réactif (computed) est une mauvaise pratique. Par défaut, Angular v19+ lève une exception NG0600 pour empêcher cela : 

❌ RuntimeError: NG0600: Writing to signals is not allowed in a `computed` or an `effect` by default.

Pourquoi cette interdiction ?

Autoriser les écritures dans les effets crée des risques élevés de boucles infinies (l'effet écrit dans un signal S1, qui déclenche un autre effet qui réécrit dans un signal S2, qui redéclenche le premier effet...). Cela détruit aussi le principe du flux d'état unidirectionnel.

❌ À éviter (Effet synchronisateur) :
effect(() => {
  const quantite = this.qty();
  // Interdit et lève NG0600 :
  this.prixTotal.set(quantite * 15); 
});
✅ Solution recommandée (Signal calculé) :
// Purement réactif et sans effet de bord :
prixTotal = computed(() => this.qty() * 15);
